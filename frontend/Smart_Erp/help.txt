2. ZERO-TRUST BIOMETRIC ENROLLMENT FIRST & SECURE QR HANDSHAKE
--------------------------------------------------------------------------------
Architectural invariant:
  1. Regular student registration MUST NEVER enroll face embeddings.
  2. Super Admin MUST register and activate the student's AES-256-GCM encrypted
     128-d SFace StudentFaceTemplate first (via Passport Photo Extraction, Live
     Webcam Capture, or High-Res Portrait Upload in Student.tsx -> FaceEnrollModal).
  3. Only after an active template exists can a student start a live liveness
     challenge and LAN handshake session.

File-by-file fixes applied:
  - PythonFaceAiClient.java:
    Parses Python FastAPI {"detail": "..."} JSON bodies cleanly on non-200 HTTP
    responses instead of swallowing diagnostic messages; smart-erp-face-ai/
    remains untouched on /internal/v1/face/*.
  - FaceVerificationService.java:
    Added strict pre-flight check in startVerification(): blocks session creation
    immediately with a clear error if StudentFaceTemplateRepository has no active
    template for the student. Removed silent runtime auto-enrollment fallback in
    processChallengeFrames() and unused FileService dependency.
  - AdminAttendanceController.java:
    Added GET /{role}/attendance/students/face-status-map so Student.tsx fetches
    real biometric readiness badges in one batch request.
  - LocalHandshakeRequest.java & LocalHandshakeService.java:
    Added teacherId, expiresAt, and companionReceiptId; aligned default QR
    expiry validation window cleanly; changed !verifyTeacherQRPayload(...) from
    warning log only into a real RuntimeException rejection; added idempotent
    handling if an active verified handshake already exists for that session.
  - AttendanceSessionService.java & TeacherAttendanceController.java:
    Bound AttendanceSessionService.startSession() to SectionAcademicCalendar and
    SectionCalendarDay so faculty cannot open attendance on an explicit CLOSED /
    non-instructional day; validated section.course and subject.course match;
    scoped /teacher/attendance/filters by authenticated teacher's university.
  - client/services/adminFaceService.ts:
    Replaced hardcoded /super-admin path prefix with dynamic getBaseUrl() and
    added getFaceStatusMap().
  - client/components/admin/FaceEnrollModal.tsx:
    Added supervised Method 2 Live Desk Webcam Capture alongside Method 1
    Official Passport Photo Extraction and Method 3 Supervised File Upload.
  - client/pages/userMangement/Student.tsx:
    Renders Face Biometrics Registered / Face Pending status badges on every row
    and triggers FaceEnrollModal using student.student.id (Students PK).
    Verified Student create dialog uploads PassportPhotoUpload only.
  - client/pages/student/StudentSecureAttendance.tsx:
    Solved identity bug where /auth/profile returned userId while WebSockets
    push to /topic/attendance/student/{studentId} (Students table PK): now loads

3. SPECIALIZATION-SCOPED TIMETABLE, CONTIGUOUS LABS & SINGLE CALENDAR
--------------------------------------------------------------------------------
Core rules enforced across backend & UI:
  1. TimetableScope.SECTION -> ONLY core subjects (specializations empty).
  2. TimetableScope.SECTION_GROUP -> ONLY specialization subjects matching
     group.getSpecialization(); never pulled into SECTION scope.
  3. Core SECTION schedule and SECTION_GROUP specialization schedule never
     assign different lectures into the same (dayOfWeek, basePeriod) student slot.
  4. Practical/Lab subjects (isPracticalSubject == true or lab keywords) allocate
     2 truly contiguous CLASS periods (period[i+1].sequenceNumber == seq + 1 AND
     periodType == CLASS), never spanning across BREAK, LUNCH, or ASSEMBLY.
  5. Exactly 1 active teacher is reused per subject within a section/group;
     teacher and room conflicts are validated across all PUBLISHED timetables.
  6. 1 SectionAcademicCalendar is logically bound per Section.

File-by-file changes applied:
  - SectionTimetableEntryRepo.java:
    Added existsByTeacherAndDayAndPeriodAndStatus() and
    existsByRoomAndDayAndPeriodAndStatus().
  - AutomaticTimetableGeneratorService.java:
    Preserves full ordered BaseTimeTablePeriod timeline so lab pairs check
    adjacent periods in allActivePeriods and reject Break/Lunch spanning;
    removed fallback pulling specialization subjects into SECTION; added
    preloadComplementarySectionSlots() to block SECTION vs SECTION_GROUP student
    slot overlaps; prioritizes RoomType.LABORATORY for practicals; spreads classes
    across weekdays and binds 1 teacher per subject.
  - TimetableManagementService.java & SectionCalendarController.java:
    Fixed getTimetable(sectionId, groupId, date) to merge published SECTION +
    SECTION_GROUP entries (previously hid core lectures when groupId was set);
    added teacher collision verification on publishVersion(); enforced
    specialization match on submitOverride(); added findCalendarBySection() and
    publishCalendar() exposed via GET /by-section/{sectionId} and
    POST /{calendarId}/publish.
  - AutoGenerateTimetableRequest.java:
    Made academicYearId optional so requests resolve section's academicYear
    cleanly when omitted.
  - client/services/timetable/sectionCalendarService.ts & AcademicCalendar.tsx:
    Removed fragile sessionStorage calendar ID cache; auto-resolves the single
    bound calendar whenever section changes; fixed local YYYY-MM-DD date
    formatting (avoiding UTC midnight shift); added Publish Calendar action.
  - client/pages/timeTable/TimetableBuilder.tsx:
    Replaced raw numeric group ID input with a SectionGroup dropdown displaying
    "GroupName — SpecializationName"; filtered manual slot subjects strictly by
    SECTION (core) vs SECTION_GROUP (matching specialization); added single-teacher
    check + 2-consecutive-period checkbox guarded against Breaks/Lunch; added an
    Auto-Generate configuration modal.
