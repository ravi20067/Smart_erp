================================================================================
SMART COLLEGE ERP — ZERO-TRUST ATTENDANCE WORKFLOW SPECIFICATION
================================================================================

Architecture Stack:
  1. React TypeScript Frontend      (frontend/Smart_Erp)
  2. Spring Boot Backend (:7777)    (backend/Smart_Erp)
  3. Python Face AI Service (:8001) (smart-erp-face-ai — FastAPI + Uvicorn)
  4. MySQL Database                 (persistent entities, templates & audit logs)
  5. Redis                          (session TTL, nonce replay protection, tokens & locks)
  6. WebSocket STOMP Broker         (real-time Teacher, Student & Guard updates)

================================================================================
END-TO-END SEQUENCE OVERVIEW
================================================================================

  [0A] Campus Gate Check-In (Students & Teachers)
       -> Security Guard verifies identity & ERP portrait for gate CHECK_IN / CHECK_OUT.
       -> Students MUST hold an approved open Campus Check-In to mark classroom attendance.
       -> Teachers have independent Campus Check-In/Out logs separate from StudentAttendance.
  [0B] Admin Face Enrollment
       -> Student must have an ACTIVE encrypted 128-D SFace template first.
  [1] Teacher HTTPS Companion & Session Start + Rotating QR
       -> Calendar-checked session (90m) + Teacher Ed25519/X25519 keys + allowlisted LAN CIDRs
          bound inside HMAC-SHA256 QR payload (60s window).
  [2] Student QR Scan + Verification Start
       -> Pre-flight checks (open campus check-in, active session, section enrollment, face template).
  [3] Active Face Liveness & 1:1 Identity Matching
       -> 3 randomized challenges via Python AI + AES-256-GCM decryption + match.
  [4] Cryptographic HTTPS Local Network (LAN) Handshake
       -> Spring Boot signed StudentHandshakeTicket + direct HTTPS TLS exchange with
          Teacher Companion (Ed25519 signatures + X25519 ECDH + HKDF-SHA256 + HMAC-SHA256)
          + private LAN/CIDR allowlist + anti-proxy header enforcement + anti-replay.
  [5] Student Classroom Check-In QR Generation
       -> Single-use Redis check-in token (5m TTL) + SecurityGuardCheckIn row.
  [6] Security Guard Scan, Visual Review & Final Attendance Decision
       -> Redis distributed lock -> Approve/Reject -> Save StudentAttendance (PRESENT).

================================================================================
PHASE 0: ADMIN FACE BIOMETRIC ENROLLMENT (MANDATORY PREREQUISITE)
================================================================================

Note: Self-enrollment by students is blocked; face biometric registration is
performed by authorized administrators only.

- Frontend UI:
    * Student management modal -> FaceEnrollModal.tsx
    * Three supervised enrollment methods:
      1. Extract directly from registered student passport photo
      2. Live supervised webcam capture at admin desk
      3. Upload clear portrait image (JPEG / PNG / WebP)
- Backend Controller (AdminAttendanceController.java):
    * Base URL: /{role:head-of-department|admin|dean|super-admin}/attendance
    * POST   /students/{studentId}/enroll-face            (multipart optional file)
    * POST   /students/{studentId}/enroll-face/from-photo (non-multipart registered photo)
    * GET    /students/{studentId}/face-status
    * GET    /students/face-status-map
    * DELETE /students/{studentId}/face-template
- Processing Flow:
    1. AdminAttendanceController loads image bytes (uploaded file or FileService
       photo from Student -> User -> BasicDetail -> FileMetadata).
    2. FaceVerificationService.enrollStudentFace calls PythonFaceAiClient
       over HTTP/1.1 POST /internal/v1/face/enrollments/extract (multipart field: images).
    3. smart-erp-face-ai (EnrollmentService):
       - YuNetFaceDetector detects faces (rejects 422 if 0 faces or >1 faces).
       - assess_quality checks sharpness (blur score), brightness & min dimensions.
       - MiniFASNetAntiSpoof runs anti-spoofing check.
       - SFaceRecognizer extracts unit-normalized 128-D face embedding.
    4. BiometricEncryptionService encrypts the 128 floats using AES/GCM/NoPadding
       (12-byte random IV + 128-bit GCM tag, SHA-256 derived key).
    5. Stored in StudentFaceTemplate (status="ACTIVE", algorithm="SFACE",
       embeddingDimension=128) and linked 1:1 on Student.assignFaceTemplate(template).
    6. Audit event logged: FACE_TEMPLATE_ENROLLED.

- Direct Student Template Status Read Endpoints:
    * GET /student/face-template            (StudentPortalController)
    * GET /student/attendance/face-template (StudentAttendanceController)
    (Returns status, algorithm, embeddingDimension, enrolledAt — never raw vectors.)

PHASE 1: TEACHER SESSION START & ROTATING QR GENERATION
================================================================================

- Frontend UI:
    * TeacherAttendanceManager.tsx (/teacher/attendance)
- Backend Controller (TeacherAttendanceController.java):
    * Base URL: /teacher/attendance
    * GET  /filters
    * POST /sessions/start
    * POST /sessions/{sessionUuid}/qr/refresh
    * GET  /sessions/active
    * GET  /sessions/{sessionUuid}/stats
    * POST /sessions/{sessionUuid}/stop
- Processing Flow (AttendanceSessionService.startSession):
    1. Resolves Teacher, AcademicYear, Course, Section, and Subject.
    2. Validates section.course == course and subject.course == course.
    3. Academic Calendar Gate: checks SectionAcademicCalendar & SectionCalendarDay
       for LocalDate.now(); blocks session startup (IllegalStateException) if
       operatingStatus == CLOSED or !instructionDay.
    4. Automatically closes any existing ACTIVE session belonging to the teacher
       and removes its Redis key.
    5. Persists AttendanceSession (status=ACTIVE, expiresAt = now + 90 minutes,
       localServerIp, localServerPort).
    6. Writes Redis session cache:
       Key: attendance:session:{sessionUuid} -> teacherId (TTL: 90 minutes).
    7. QRTokenService.generateTeacherQRPayload builds JSON payload valid for 60s:
       Fields: sessionId, teacherId, localServerIp, localServerPort,
               timestamp, expiresAt, nonce (UUID), signature (HMAC-SHA256 over fields).
    8. Audits ATTENDANCE_SESSION_STARTED and broadcasts WebSocket event.
    9. Teacher UI refreshes rotating QR via POST /sessions/{sessionUuid}/qr/refresh
       while keeping the same classroom attendance session active.

================================================================================
PHASE 2: STUDENT QR SCAN & FACE VERIFICATION INITIALIZATION
================================================================================

- Frontend UI:
    * StudentSecureAttendance.tsx (/student/attendance)
    * Subscribes to WebSocket topic: /topic/attendance/student/{studentId}
- Backend Endpoint (StudentAttendanceController.java):
    * POST /student/attendance/verification/start
- Gate Checks (FaceVerificationService.startVerification):
    1. AttendanceSession exists, status == ACTIVE, and now <= expiresAt.
    2. Student does not already have a StudentAttendance row in this session.
    3. Student holds a StudentEnrollment mapped to session.getSection().
    4. Mandatory Biometric Gate: Student must have an ACTIVE StudentFaceTemplate
       with non-blank encrypted embedding (checked via Student.getFaceTemplate() /
       StudentFaceTemplateRepository).
- Initialization:
    1. ChallengeGenerationService builds a 3-step sequence:
       - Step 1 (always): LOOK_STRAIGHT (baseline + comparison pose)
       - Steps 2 & 3 (shuffled from): BLINK_TWICE, TURN_LEFT, TURN_RIGHT, LOOK_UP, LOOK_DOWN
    2. Saves FaceVerificationSession (sessionId="FVS-...", status=IN_PROGRESS,
       maxAttempts=6, expiresAt = now + 2 minutes).
    3. Calls PythonFaceAiClient.createSession -> POST /internal/v1/face/sessions (120s TTL).
    4. Audits & broadcasts LIVENESS_STARTED; returns verificationSessionId + first prompt.

================================================================================
PHASE 3: ACTIVE LIVENESS CHALLENGES & 1:1 SFACE IDENTITY MATCHING
================================================================================

- Frontend Capture Loop:
    * Captures bursts of 3 JPEG webcam frames and submits sequentially to:
      POST /student/attendance/verification/{verificationSessionId}/challenge
      (params: action, sequenceNumber, multipart part: frames)
- Processing Flow (FaceVerificationService.processChallengeFrames):
    1. Verifies verification session belongs to authenticated student and has not expired.
    2. Enforces strict challenge sequence order (must match currentChallengeIndex).
    3. Increments totalAttempts (if totalAttempts >= 6 maxAttempts, marks FAILED).
    4. Forwards frames over HTTP/1.1 to Python Face AI:
       POST /internal/v1/face/sessions/{sessionId}/frames
       (YuNet detection + MediaPipe pose/blink + MiniFASNetV2 anti-spoof).
    5. Saves FaceVerificationAttempt with acceptance, confidence, and observations.
    6. When accepted and more challenges remain -> advances currentChallengeIndex
       and returns nextChallenge + nextChallengeDescription.
    7. When ALL 3 challenges pass:
       - Calls POST /internal/v1/face/sessions/{sessionId}/complete to extract
         live captured_embedding (128 floats).
       - Decrypts student's stored StudentFaceTemplate embedding via AES-256-GCM.
       - Calls PythonFaceAiClient.compareEmbeddings -> POST /internal/v1/face/compare
         (cosine similarity).
       - Compares similarity >= app.face-ai.match-threshold (default: 0.363):
         * MATCH    -> FaceVerificationSession.status = PASSED, audits & broadcasts
                       IDENTITY_VERIFIED.
         * MISMATCH -> FaceVerificationSession.status = FAILED, audits & broadcasts
                       IDENTITY_FAILED, aborts attendance flow.

================================================================================
PHASE 4: CRYPTOGRAPHIC HTTPS LOCAL NETWORK HANDSHAKE & ANTI-REPLAY
================================================================================

- Teacher Companion Process (frontend/Smart_Erp/scripts/start-handshake-companion.mjs):
    * Binds strictly to Teacher RFC 1918 / ULA private LAN IP over HTTPS (TLS SAN cert).
    * Holds ephemeral in-memory Ed25519 + X25519 keys wiped on session stop or exit.
    * Rejects public IPs, non-allowlisted subnets, and proxy headers (X-Forwarded-For,
      Forwarded, Via, X-Real-IP, CF-Connecting-IP).
- Frontend Action (StudentSecureAttendance.tsx + handshakeCrypto.ts):
    1. Generates ephemeral WebCrypto Ed25519 & X25519 keypairs + CSPRNG studentNonce.
    2. Requests single-use Spring Boot Ed25519-signed ticket:
       POST /student/attendance/handshake/ticket
    3. Exchanges POST https://{teacherServerIp}:{port}/handshake/challenge and
       /handshake/complete directly over classroom LAN TLS using X25519 + HKDF-SHA256
       and mutual Ed25519 signatures.
    4. Submits companion-signed receipt + proof chain to Spring Boot:
       POST /student/attendance/handshake/verify
- Backend Checks (LocalHandshakeService.verifyHandshake):
    1. Enforces no forwarding/proxy headers (LocalNetworkPolicy).
    2. Confirms active open Campus Check-In + AttendanceSession ACTIVE + Face PASSED.
    3. Verifies Student identity reference, Teacher ID, pinned Teacher Ed25519/X25519 keys,
       and full Teacher QR HMAC signature.
    4. Validates both Teacher LAN IP & Peer Client IP against RFC 1918/ULA & allowedSubnets.
    5. Consumes single-use backend ticket, verifies Student Ed25519 proof signature,
       and independently verifies Teacher Companion Ed25519 receipt signature.
    6. Guards concurrency via Redis distributed lock (lock:handshake:{session}:{student})
       and consumes all nonces/receipts atomically in Redis + DB.
    7. Persists LocalHandshakeRecord, caches receipt, audits & broadcasts HANDSHAKE_VERIFIED.

================================================================================
PHASE 5: STUDENT GATE CHECK-IN QR GENERATION
================================================================================

- Frontend Action:
    * Requests Security Guard gate QR code:
      GET /student/attendance/checkin/qr?sessionUuid={sessionUuid}
- Backend Processing (CheckInService.generateStudentCheckInQR):
    1. Confirms AttendanceSession is ACTIVE and attendance is not already marked.
    2. Gate 1: confirms FaceVerificationSession (status=PASSED).
    3. Gate 2: confirms LocalHandshakeRecord exists.
    4. Generates single-use token via QRTokenService.generateCheckInToken:
       Key: attendance:checkin_token:{token} -> {sessionUuid}:{studentId} (TTL: 300s / 5m).
    5. Saves SecurityGuardCheckIn (status=PENDING, expiresAt = now + 5 minutes).
    6. Logs & broadcasts GUARD_CHECKIN_PENDING (notifies guard terminals via
       /topic/attendance/guard).
    7. Returns StudentCheckInQRResponse with qrData = "CHECKIN:" + token.

================================================================================
PHASE 6: SECURITY GUARD CHECK-IN SCAN & AUTHORITATIVE ATTENDANCE MARKING
================================================================================

- Frontend UI:
    * SecurityGuardCheckIn.tsx (/security-guard/check-in)
    * Subscribed to /topic/attendance/guard for pending check-in alerts.
- Backend Controller (SecurityGuardCheckInController.java, /security-guard/check-in):
    * POST /scan
    * POST /decision
    * GET  /photo/{studentId}  (streams official registered student portrait)
- Step 6A — Guard Scans Student QR (GuardApprovalService.scanStudentCheckIn):
    1. Strips "CHECKIN:" prefix and resolves SecurityGuardCheckIn (must be unexpired).
    2. Loads student profile details, face verification pass flag & similarity score,
       handshake verification flag, and secure /security-guard/check-in/photo/{studentId} URL.
    3. Guard visually verifies student physically matches ERP profile portrait.
- Step 6B — Guard Decision (GuardApprovalService.processGuardDecision):
    1. Acquires Redis distributed lock:
       Key: lock:guard_decision:{token} (SETNX TTL: 10s, deleted in finally block)
       to prevent race conditions across concurrent guard scanners.
    2. Ensures SecurityGuardCheckIn.status == PENDING.
    3. Branch A — Rejected (approved == false):
       - Requires non-blank rejectionReason.
       - Updates status=REJECTED, saves reason/guard/timestamp, deletes Redis
         attendance:checkin_token:{token}, audits & broadcasts GUARD_REJECTED.
       - Attendance is NOT marked.
    4. Branch B — Approved (approved == true):
       - Updates status=APPROVED, deletes Redis check-in token, audits & broadcasts
         GUARD_APPROVED.
       - Calls AttendanceDecisionService.evaluateAndMarkAttendance.
- Step 6C — Final Attendance Recording (AttendanceDecisionService):
    1. Re-validates all gates atomically:
       - No duplicate StudentAttendance for (session, student)
       - Session ACTIVE and unexpired
       - Student enrolled in session's Section
       - FaceVerificationSession PASSED
       - LocalHandshakeRecord present
       - SecurityGuardCheckIn APPROVED
    2. Saves StudentAttendance (status=PRESENT, similarityScore, faceVerificationSessionId,
       handshakeReceiptId, guard, guardDecisionTime, clientIp).
    3. Audits ATTENDANCE_MARKED and broadcasts ATTENDANCE_MARKED over WebSocket.
